# 种子地图内核（cubiomes 的 Java 复刻）设计稿

> 目标：把「群系 / 结构」的种子查询从"跑一个真服务端"换成纯 Java 计算，
> 从分钟级降到毫秒级，并且可以任意缩放、任意范围。
>
> 状态：**设计稿**（未开工）。现有实现见 [seed-preview.md](seed-preview.md)。

## 1. 为什么

现在的种子预览是真的起一个 `server.jar` 生成世界，再读 region 文件。它准确，
但慢，而且慢得没有优化空间——实测（1.14.4，4096 区块）：

| 数据 | 值 |
|---|---|
| 单区块生成 | 15–20 ms |
| 1024×1024 格（4096 区块） | 60–90 秒 |
| 8192×8192 格（65536 区块） | 20–30 分钟 |

问题不在"Java 慢"，在**服务端在生成整个世界**：方块、光照、实体、特性、落盘。
而种子地图真正需要的只有一件事：给定 `(seed, x, z)`，这里是哪个群系、附近有没有村庄。

cubiomes 把这件事做成了纯计算：

| 方式 | 8192×8192 格（16 格/采样点，262k 点） |
|---|---|
| 真服务端 | 20–30 分钟 |
| cubiomes（C） | ≈ 0.5 秒 |
| 本设计（Java 复刻） | ≈ 1–2 秒 |

三个数量级。JIT 之后的 Java 跑这种 float 噪声循环通常只比 C 慢 1–3 倍，
而算法本身不生成任何东西——这才是差距的来源。

## 2. 边界

**做**

- 主世界的生物群系查询：`biomeAt(version, seed, x, z)`，任意坐标；
- 结构位置：村庄、沙漠/丛林神殿、女巫小屋、林地府邸、海底神殿、海底废墟、
  沉船、废弃传送门、掠夺者前哨、远古城市、试炼密室、要塞、矿井；
- 史莱姆区块（纯公式，已有）、出生点、要塞同心环；
- 版本族：先 1.21.x、1.16.5、1.14.4 三档，之后按需扩展。

**不做（v1）**

- 地形高度、方块、光照——那是渲染问题，继续由真服务端负责；
- 下界与末地（v1 只做主世界）；
- 维度切换、实体的生成判定；
- 自定义维度/数据包。

**不做（永远）**

- 从反编译源码抄代码。见 §7。

## 3. 来源与许可

实现移植自 [Cubitect/cubiomes](https://github.com/Cubitect/cubiomes)（**MIT**）。
`cubiomes-viewer` 是它的 Qt 前端，与本设计无关，只当效果参考。

反编译的 Minecraft 源码（`/data/MCP-Reborn-1.21`）**只用于回答"为什么这个数是
这个"**，以及构造验证器。它的许可证明确禁止发布派生源码，所以：

- 进产品的代码只能来自 cubiomes（MIT）；
- 反编译源码只在测试代码里以"调用游戏自带的群系源"的形式出现，不复制进实现。

## 4. 结构

新增包 `org.jackhuang.hmcl.web.minecraft.cubiomes`：

```
Noise.java           Perlin / simplex、八度叠加、xoroshiro 随机
BiomeNoise.java      1.18+ 的气候噪声与 multi-noise 查表；1.7–1.17 的层栈
BiomeTable.java      每个版本的群系参数表（生成，不手抄）
Generator.java       层栈生成器、结构放置（spacing / separation / salt）
Finder.java          结构定位（从中心向外找最近的满足条件的起点）
World.java           门面：biomeAt() / structures() / spawn() / strongholds()
VersionFamily.java   版本分支：LEGACY(≤1.17) / MODERN(≥1.18)
```

与现有代码的关系：

```
SeedPreviewService
 ├─ ServerBackend   （现有）真服务端生成 → region → 详细地图 / 地面真值
 └─ JavaBackend     （新）cubiomes 复刻 → 群系 / 结构 → 速览图
```

前端「群系速览」切到 `JavaBackend`；「详细地图」保持 `ServerBackend`。
两者并存，`ServerBackend` 同时充当验证基准。

## 5. 数据表怎么来（关键）

风险最大的不是算法，是**表**：每个版本几十个群系的温度/湿度/大陆性/侵蚀/深度/
怪异度区间，以及噪声参数。手抄必错。

做法：写一个一次性代码生成器，从 cubiomes 的 C 源码解析出表，生成
`BiomeTable_1_21.java` 之类的常量类。

```
tools/cubiomes-gen/         （不进发布物）
  parse.c 或 python 脚本    读 cubiomes 的 biomes.c / biomenoise.c
  → 生成 src/main/java/.../cubiomes/gen/Table_*.java
```

生成出来的代码带注释标注来源（cubiomes 版本 + 提交号），便于追溯。

## 6. 三层验证

这是本设计能成立的前提。三层缺一不可：

| 层 | 对比对象 | 规模 | 判定 | 目的 |
|---|---|---|---|---|
| **L1** | Java 版 ↔ cubiomes C 版 | 百万级采样点，逐点比对 | **必须完全一致** | 抓移植错误；纯自动，几十秒跑完 |
| **L2** | Java 版 ↔ 游戏自带的群系源 | 每版本几十个种子，边界密集采样 | 必须一致（或登记为已知偏差） | 抓 cubiomes 本身与该版本的偏差 |
| **L3** | Java 版 ↔ 真服务端生成的区块 | 几十个种子，整块区域 | 必须一致 | 端到端回归，覆盖结构与渲染链路 |

### L1：对 C 版

cubiomes 能编出一个只做查询的小程序（或 JNI 只用在测试里）。采样策略：

- 随机种子 × 随机坐标；
- **边界密集**：先用 C 版找出群系边界，再在边界 ±8 格内密集取点——绝大多数
  移植错误出现在边界判定（`<=` 与 `<`、参数区间端点的开闭）。

### L2：对游戏本体

写一个测试工具，`Bootstrap.bootStrap()` 之后按世界预设构造
`net.minecraft.world.level.biome.MultiNoiseBiomeSource`（1.18+）或
`GenLayer` 栈（≤1.17），直接问任意坐标的群系，不生成区块。

这一步依赖反编译源码里的类名/字段名（官方 mappings 也行），但**只读**。
反编译源码在这里的第二个用途：当 L2 出现差异时，去读对应版本的
`OverworldBiomeBuilder` / `Climate` 确认到底谁对。

### L3：对真服务端

复用现有 `SeedPreviewService`：固定种子跑一块区域，读每个区块的 `Biomes`，
与 Java 版逐格比对。慢，但它是唯一的"跑在真实游戏里"的证据。

### 验收门槛

- L1 差异 = 0；
- L2 差异 = 0，或差异全部登记进 `docs/cubiomes-java-deviations.md` 并说明原因；
- L3 差异 = 0。

任何一层不过，该版本标记为"实验性"，前端不给它切 Java 后端。

## 7. 性能目标

| 场景 | 目标 |
|---|---|
| 单点 `biomeAt` | < 5 µs |
| 1024×1024 格 @ 4 格/点（256² 点） | < 1 秒 |
| 8192×8192 格 @ 16 格/点（512² 点） | < 3 秒 |
| 结构查询（单类型，半径 2048） | < 100 ms |

实现纪律：

- 噪声循环里不分配对象，全部用 `double[]` / `int[]`；
- 群系查表用 `short` 索引而不是字符串；
- 结果按 256×256 格的瓦片缓存，平移时不重算。

## 8. 前端与缓存

- `PreviewSpec.Mode` 增加 `FAST_BIOME`；`SeedPreviewService` 按模式选后端。
- 速览图按瓦片返回（`/api/mc/preview/tile?version&seed&z&x&zoom`），前端按视口请求，
  而不是"点一次生成一张大图"。
- 详细图仍是整块生成 + 整图返回，保留现有交互。

## 9. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| M1 | `Noise` + `BiomeNoise` + 1.21 表；L1 验证器跑通 | 1.21 的 L1 全绿 |
| M2 | 1.16.5 / 1.14.4 的层栈；L1 覆盖三个版本 | 三版本 L1 全绿 |
| M3 | `Finder`：村庄/神殿/要塞；L2/L3 抽检 | 结构与服务端一致 |
| M4 | 前端瓦片接入、缓存、图例 | 缩放平移无卡顿 |

## 10. 风险

| 风险 | 应对 |
|---|---|
| 表抄错 | 用生成器而不是手抄；L1 卡住 |
| 1.18+ multi-noise 复杂（6 维气候 + 密度函数） | 先只做群系，结构后置；一次只加一个版本 |
| cubiomes 对某个小版本本身不准 | L2 发现 → 登记偏差 → 该版本回退到服务端后端 |
| 版本矩阵失控 | 一次只支持一个版本，三层全过才发布 |
| 许可 | 只从 MIT 的 cubiomes 取；反编译源码不进实现 |
| 与真服务端结果不一致被用户发现 | L3 常驻 CI；不一致的版本前端显式标注"实验性" |

## 11. 待定

1. 结构是否进 v1：村庄和要塞的收益最大，但 `Finder` 的工作量约占 30%。
2. 瓦片尺寸与缓存淘汰策略。
3. 是否保留 JNI 作为"对照组"长期存在（只用于测试，不进发布物）。
4. 版本支持范围：是否要覆盖 1.12.2 及更早（层栈差异更大）。
